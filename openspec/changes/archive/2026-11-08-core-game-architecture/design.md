# Design

## Context

См. `proposal.md` — Why. Поведенческие контракты находятся в `specs/scene-management/spec.md`, `specs/render-extraction/spec.md` и `specs/frame-scheduling/spec.md`.

Реализованы Math Point/Vector и Object Library. `Geometry` является закрытым `std::variant`; фабрики возвращают владеющие значения через `std::expected`. Mesh, Polyline и Polygon владеют STL-контейнерами, их копирование создаёт независимые данные, а `std::span` только предоставляет чтение. Тесселяция отделена от создания и может быть значительно дороже передачи дескриптора кадра.

Core, Render Contracts, Runtime, Renderer, Image и адаптеры пока являются проектируемыми компонентами. Существующая документация уже закрепляет Core как владельца сцены и независимый снимок для Renderer, но допускает полное владение данными снимка и не перекрывает подготовку следующего кадра с текущим рендерингом. Для выбранной игровой нагрузки эти два пункта необходимо уточнить до начала реализации.

Целевой профиль: простая игра с 3D-миром, самостоятельным 2D-миром и экранным HUD; статическое окружение сосуществует с динамическими объектами. Визуальный минимум важнее поддержки огромных сцен, а производительность достигается прежде всего исключением повторной работы и лишних копий.

## Goals / Non-Goals

**Goals:**

- Детерминированный single-writer Core без блокировок внутри горячего пути сцены.
- Плотная обработка transforms, bounds и flags; стабильные внешние ObjectId.
- Отсутствие копий вершин и индексов при создании экземпляров и подготовке кадров.
- Тесселяция только при изменении геометрии или параметров качества.
- Полный независимый снимок с явными 3D, 2D world и HUD passes.
- Перекрытие prepare/render при не более чем одном активном и одном подготовленном кадре.
- Явное владение ресурсами снимка и framebuffer во всех сценариях, включая ошибки и остановку.
- Контракты, достаточные для depth-based 3D, материалов, базового света и 2D alpha/layers.

**Non-Goals:**

- Полная реализация игрового движка, физики, скриптинга, редактора и оконной системы в одном change.
- ECS, актор на объект, глобальная event bus или динамическая система плагинов.
- Постоянная реплика сцены Renderer и протокол дельт как начальное решение.
- PBR, текстуры, тени, post-processing и полный набор graphics-функций в первом вертикальном срезе.
- Изменение существующего API Object Library или скрытое добавление потоков и кешей в него.
- Выбор внешней акторной или оконной библиотеки как предварительное условие Core.

## Decisions

### 1. Сохранить границы модулей и разделить поток данных с зависимостями кода

```text
UI / Editor --------------------------+
                                     |
Game input --> Gameplay systems --> Runtime / Orchestrator
                                     |
                                     | synchronous C++ calls
                                     v
                              Core + Render Preparation
                                     |
                                     | synchronous values / operations
                                     v
                              Object Library + Math

Runtime --> Renderer adapter --> Renderer
Runtime <-- completions ------- Renderer adapter
Runtime --> Window / Presentation
```

Зависимости кода направлены от Runtime к Core и портам адаптеров, от Core к Object Library, Math и Render Contracts. Renderer и Window зависят от данных Render Contracts/Image, а не от Core. Обратные FrameReady/FrameFailed не создают обратной include-зависимости.

Render Preparation остаётся внутренней частью Core на первом этапе, потому что ей нужен эффективный доступ к плотному хранилищу и кешам. Она не отправляет сообщения и не растеризует. Выделение в отдельную CMake-цель оправдано только появлением независимых потребителей или необходимостью ограничить зависимости реализации.

**Альтернатива:** отдельный сервис/актор Render Preparation. Отклонена для начального контура: добавляет передачу владения и синхронизацию, но сама по себе не ускоряет обход сцены.

### 2. Core имеет одного писателя; игровой путь не проходит через editor-очередь

UI, Runtime, игровые системы и Core исполняются на главном потоке первой реализации. Изменение сцены разрешено только в фазах команд и update. Renderer никогда не вызывает Core из рабочего потока.

Для редактора сохраняется ограниченная очередь команд с `requestId` и результатом постановки. Игровые системы вызываются Runtime внутри фиксированного `Core.update(h)` либо формируют пакет изменений, применяемый в той же фазе. Движение персонажа не превращается в асинхронное сообщение на каждый объект.

Если позже появятся внешние потоки-продуценты, они используют одну ограниченную очередь, которую главный поток выгребает перед apply. Это не меняет single-writer Core.

**Альтернатива:** параллельное изменение независимых объектов. Отложено: требует правил зависимостей, синхронизации иерархии и воспроизводимости. Для простой игры сначала измеряется однопоточный update.

### 3. Плотные горячие массивы отделены от ресурсов и editor-данных

Логическая модель Core:

```text
Scene
  ObjectId <-> slot with generation
  hot arrays:
    local transform, world transform
    parent / hierarchy links
    local bounds, world bounds
    visibility, mobility, dirty flags
    geometry and material references
  cold data:
    name, editor metadata, debugging information
  resources:
    immutable Geometry versions
    immutable prepared render geometry
    immutable materials
```

ObjectId содержит индекс слота и поколение. Внутренние массивы могут использовать swap-remove; sparse-таблица обновляет связь ObjectId с новым индексом. Внешние ID и поколения не переиспользуются небезопасно.

Mobility Static/Dynamic является подсказкой. Static исключает объект из обычного динамического обхода, но явная команда всё равно помечает его dirty. Не создаются две несовместимые модели сцены.

Локальная геометрия не дублируется в SceneObject. Экземпляр хранит GeometryId и собственные transform/material/visibility. Иерархия использует внутренние индексы, а наружу выдаются только ObjectId. Удаление родителя рекурсивно удаляет поддерево атомарно.

**Альтернативы:**

- AoS SceneObject с Geometry по значению: проще, но увеличивает элемент горячего обхода и провоцирует копии.
- ECS: не выбран без требования динамического состава компонентов; плотные массивы можно получить без ECS framework.

### 4. Неизменяемые ресурсы передаются через владельцев, а не через голые views

При создании Core перемещает результат Object Library в неизменяемый ресурс. Для первой реализации используется `std::shared_ptr<const T>` для тяжёлых Geometry, TessellatedGeometry и Material. Изменение ресурса означает создание новой версии, а не мутацию опубликованного значения.

`RenderSnapshot` перемещается в задание и содержит:

- scene/render revision;
- размеры изображения и параметры очистки;
- упорядоченные render passes и камеры;
- компактные draw items;
- таблицу владельцев geometry/tessellation/material;
- небольшие значения света и параметров композиции.

Draw item хранит индекс ресурса в таблице снимка, world transform, material index и flags. Несколько экземпляров ссылаются на один ресурс. `shared_ptr` не дублируется в каждом draw item без необходимости.

Renderer получает `span` только после того, как задание уже удерживает соответствующего владельца. Snapshot не содержит `span` или указатели на изменяемые массивы Core.

**Альтернативы:**

- Полная owning-копия mesh на снимок: отклонена из-за пропускной способности памяти и аллокаций.
- Core-owned store с epoch reclamation: потенциально дешевле по refcount, но сложнее. Рассматривается после профиля; одних GeometryId без механизма удержания недостаточно.

### 5. Версии и dirty state исключают повторную работу

Core различает как минимум изменения geometry, local transform, world transform, bounds, material, visibility, camera и surface. Одна общая scene version не используется для инвалидации всех кешей.

Правила:

- local transform изменился: dirty мировое поддерево и связанные world bounds;
- geometry изменилась: dirty local bounds и tessellation соответствующего ресурса;
- transform изменился: tessellation остаётся действительной;
- material изменился: обновляется draw item, геометрия не перестраивается;
- camera/surface изменились: повторяются culling и параметры кадра, не локальная тесселяция;
- visibility изменилась: обновляются очереди, не mesh.

Локальные bounds вычисляются один раз на версию Geometry. World bounds получаются преобразованием local bounds; обход всех вершин для повторного bounds на каждом движении не требуется.

Ключ tessellation включает неизменяемую идентичность/версию Geometry и все параметры, влияющие на результат. `maxPrimitiveCount` учитывается как часть входа операции. Экземпляры одной геометрии с эквивалентным качеством используют один результат.

Для camera-dependent LOD применяются дискретные уровни качества. Непрерывный пересчёт maxDeviation от расстояния до камеры не допускается в горячем пути без отдельного профиля и политики кеша.

Фоновая тесселяция допускается только над стабильным неизменяемым входом. Результат содержит geometry version и quality key; применяет результат только Core в главном потоке и только при совпадении версии. Рабочий поток не изменяет Scene или cache напрямую.

### 6. 3D, самостоятельный 2D и HUD представлены упорядоченными passes

Core поддерживает три вида render-контекста:

- `World3D`: 3D transforms, 3D camera, meshes, materials, lights и depth;
- `World2D`: мировые 2D transforms и независимая 2D camera;
- `Hud2D`: screen-space transforms, слои и alpha без влияния игровой камеры.

Снимок содержит упорядоченный список passes, а Renderer исполняет его без вывода семантики из `Geometry::index()`. Для 2D-only игры активны World2D и Hud2D; для 3D-only — World3D и Hud2D. При одновременном 3D и самостоятельном 2D-мире порядок задаётся конфигурацией сцены; HUD завершает композицию, если явно не задан иной экранный порядок.

2D world и HUD используют одну базовую механику render-ресурсов, но разные пространства и правила сортировки. Нет необходимости искусственно встраивать HUD в 3D-сцену.

### 7. Визуальный минимум отделён от геометрической библиотеки

Object Library продолжает отвечать только за геометрию. Core владеет назначением материалов, камерами, видимостью и светом; Render Contracts переносит их значения/владельцев.

Начальный вертикальный срез предполагает:

- perspective/orthographic cameras;
- depth buffer и backface culling для 3D;
- цветовые материалы, ambient и один направленный свет;
- flat shading как минимальный освещённый вариант;
- явный layer/order и alpha blending для 2D/HUD;
- внутренний framebuffer, который Window может масштабировать при показе.

Производные нормали или другие повторно используемые shading-данные создаются и кешируются на версию render-ресурса, а не вычисляются заново без необходимости в каждом кадре. Smooth normals, UV, textures, shadows и post-processing расширяют контракт отдельными изменениями.

Числовое представление Math/Object Library в этом change не меняется. Переход render-ресурсов на float рассматривается только после отдельного анализа точности и профиля, а не как неявное следствие производительности.

### 8. Полный лёгкий снимок выбран вместо реплики Renderer

Каждый submitted кадр самодостаточен. Постоянная сцена Renderer отсутствует. Подготовка включает dirty updates, culling и построение компактных draw lists; тяжёлые ресурсы разделяются.

Стоимость остаётся O(числа видимых объектов) на draw list, но исключает O(числа вершин) копирование и повторную тесселяцию. Для простой игры это основной компромисс между пропускной способностью и сложностью.

Если prepare всё ещё доминирует после кеширования, следующие варианты оцениваются по замерам:

1. повторное использование неизменных draw-list blocks;
2. разбиение сцены на стабильные чанки;
3. реплика Renderer с дельтами, версиями, удалениями и resync.

Дельта-протокол не является автоматическим улучшением: он не ускоряет растеризацию и добавляет состояние, которое может рассинхронизироваться.

### 9. Один активный и один prepared кадр перекрывают работу без очереди

```text
Main thread:
  events/resize --> completions --> commands --> bounded update --> prepare
                                                               |
                                                               v
                                                   prepared snapshot: 0..1
                                                               |
Worker:                                                        v
                                                   active render: 0..1
                                                               |
                                                               v
                                                         completion
```

Пока Renderer занят и prepared-пуст, Core может подготовить следующий снимок. Пока prepared занят, новые снимки не создаются; изменения остаются в Core и попадут в последующий prepare. После обработки completion prepared-снимок может быть отправлен сразу.

Этот вариант выбирает пропускную способность и отсутствие потраченной подготовки: prepared-снимок не заменяется каждым более новым состоянием. Цена — отставание отображения примерно на один кадр при непрерывных изменениях. Политика latest-ready с выбрасыванием ещё не отправленных снимков рассматривается только при измеренной проблеме latency.

`trySubmit` остаётся неблокирующим. Accepted перемещает snapshot и устанавливает pendingFrame; Rejected оставляет оба ресурса у Runtime. Канал completion резервирует слот на принятое задание, RendererDown имеет отдельный надёжный путь.

### 10. Framebuffer имеет уникального владельца и явный цикл возврата

Image владеет типом ImageBuffer; Runtime владеет небольшим пулом буферов главного цикла. RenderFrame получает unique ownership буфера вместе со snapshot. Renderer только записывает в переданный буфер и возвращает его в FrameReady или FrameFailed.

После FrameReady Runtime либо отбрасывает буфер, либо передаёт Presentation. Возврат в пул разрешён после синхронного `present`; для асинхронного Presentation требуется отдельное completion. При FrameFailed буфер также возвращается вместе с ошибкой. При RendererDown ресурсы не переиспользуются до подтверждения прекращения исполнения и безопасной уборки адаптера.

Размер пула определяется максимальным числом одновременно живых буферов: active render, presentation и при необходимости один дополнительный слот. Не создаётся очередь свободных кадров сверх этой потребности. Resize создаёт буферы нового формата/размера, старое поколение освобождается после окончания использования.

### 11. Проверяемость и измерения являются частью подхода

Синхронный Renderer сохраняется как эталон для сравнения изображений и упрощения тестов, даже если основной путь асинхронный. Транспортные сценарии проверяются fake Renderer без реальной растеризации.

Минимальная телеметрия для профиля:

- длительность command apply, update, prepare, render и present;
- число объектов, видимых draw items, triangles и активных ресурсов;
- число вызовов bounds/tessellate на версию Geometry;
- число и размер выделений/копий на кадр;
- глубина active/prepared и причины отказов;
- число dirty updates и отброшенных игровых шагов.

Обязательные нагрузочные профили: статическая сцена, массовое движение экземпляров одной геометрии, частая замена геометрии, 2D-only, 3D+HUD, смешанный 2D/3D и медленный Renderer.

## Risks / Trade-offs

- **Atomic refcount и pointer chasing shared_ptr станут заметны** → снимок группирует ресурсы в таблице; при подтверждённом профиле рассматривается versioned store с удержанием кадровых поколений.
- **Полный draw list останется дорогим на очень большой сцене** → сначала culling и повторное использование blocks; реплика/delta только после доказанной необходимости.
- **Ошибка dirty propagation создаст устаревший кадр** → тесты изменения каждого входа и debug-режим полного пересчёта для сравнения с инкрементальным результатом.
- **Фоновая тесселяция завершится после новой правки** → версии входа и commit только Core; устаревший результат уничтожается без публикации.
- **Prepared-снимок добавит latency** → строго один слот и немедленная отправка после completion; не накапливать ещё один latest-снимок без отдельного решения.
- **Пул framebuffer вернёт используемый Window буфер** → уникальный ownership token и обязательное presentation completion для удерживающего API.
- **Визуальные требования раздутают первый этап** → вертикальный срез ограничен depth, цветовыми материалами, базовым светом и 2D alpha/layers.
- **Параллелизм создаст больше накладных расходов, чем выигрыша** → начальный single-writer и ограниченные фоновые задачи только по профилю.
- **Остановка зависнет при сбое актора** → отдельный RendererDown, подтверждение прекращения исполнения и запрет освобождения по одному таймауту.

## Migration Plan

1. **Контракты и математическая основа.** Добавить необходимые transforms/camera values, Render Contracts и ImageBuffer с тестами владения. Сохранить Object Library без изменений.
2. **Минимальный Core.** Реализовать ObjectId/generation, плотное хранилище, иерархию, mobility, GeometryStore, атомарные команды и fixed update. Проверить ошибки и stale IDs.
3. **Render Preparation.** Добавить версии, dirty updates, bounds/tessellation cache, resource-owning snapshots и World3D/World2D/Hud2D passes. Проверять без реального Renderer.
4. **Синхронный эталон.** Собрать headless-путь Core → snapshot → fake/synchronous Renderer для проверки содержимого и визуального минимума.
5. **Асинхронный Runtime.** Добавить Renderer Port, Accepted/Rejected, completions, frameId, RendererDown, resize и остановку через fake adapter.
6. **Перекрытие и пул.** Включить один prepared-снимок и явный framebuffer return; проверить медленный Renderer, ошибки, resize и close.
7. **Игровой вертикальный срез.** Проверить простую 2D-сцену с HUD и простую 3D-сцену с динамическими объектами, светом и HUD. Сравнить sync/async результат.
8. **Профилирование.** Зафиксировать baseline и только затем принимать решение о фоновой тесселяции, chunks, epochs или Renderer replica.

Каждый шаг оставляет работающее промежуточное состояние. Синхронный путь служит fallback при проблемах адаптера; откат асинхронной доставки не меняет Scene или Object Library. Публичные контракты вводятся инкрементально до расширения визуальных функций.
