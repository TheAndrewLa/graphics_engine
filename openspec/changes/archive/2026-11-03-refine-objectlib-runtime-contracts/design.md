# Design

## Context

Object Library уже предоставляет typed-перегрузки операций и runtime-фабрику над `Geometry`, но не runtime-операции. `Geometry` включает 23 значения разных размерностей и возможностей; Line, Ray и Plane не имеют конечных bounds, а тесселяция определена только для пяти параметрических фигур. Math Point остаётся публичным агрегатом и может измениться после проверки фабрикой.

Проектные ограничения: сохранить C++23, value semantics, `std::expected`, отсутствие скрытого состояния и зависимость Object Library только от Math и STL. Существующие публичные сигнатуры и численные алгоритмы не меняются.

## Goals / Non-Goals

**Goals:**

- Централизовать разбор `Geometry` для bounds и тесселяции.
- Вернуть однозначные variant-результаты без общего базового класса.
- Делегировать всю валидацию и вычисления существующим typed-операциям.
- Явно обработать неподдерживаемые альтернативы и `valueless_by_exception`.
- Сохранить независимое владение результатов и текущие координатные правила.

**Non-Goals:**

- Не вводить checked-обёртку Point, общий `RenderableGeometry`, преобразования или Runtime API для всех существующих и будущих операций.
- Не централизовать сейчас каталог ObjectType/traits и не менять алгоритмы, сложность, формат ошибок или политику исключений.

## Decisions

### 1. Отдельные variant-результаты вместо универсального типа

В `operations/bounds.h` добавляются:

```cpp
using BoundsGeometry = std::variant<Aabb2, Aabb3>;
using RuntimeBoundsResult = GeometryResult<BoundsGeometry>;
[[nodiscard]] RuntimeBoundsResult bounds(const Geometry& geometry);
```

В `operations/tessellate.h` добавляются:

```cpp
using TessellatedGeometry = std::variant<Polyline2, TriangleMesh2, TriangleMesh3>;
using RuntimeTessellationResult = GeometryResult<TessellatedGeometry>;
[[nodiscard]] RuntimeTessellationResult tessellate(const Geometry& geometry,
                                                    TessellationOptions options = {});
```

Это сохраняет конкретный тип результата и не смешивает 2D с 3D внутри одного Aabb или Mesh. Альтернатива — шаблонный visitor в каждом потребителе — не решает дублирование диспетчеризации. Общий базовый Object отвергается: он добавил бы неоднородные виртуальные операции и владение через указатели без необходимости.

### 2. Тонкая runtime-диспетчеризация через std::visit

Определения размещаются в новом `src/operations/runtime_operations.cpp`, подключаемом к `huynity_objectlib`. Каждая операция сначала проверяет `geometry.valueless_by_exception()` и возвращает `InvalidGeometry`.

Обобщённый visitor получает конкретную альтернативу как `const auto&`:

- для bounds вызывается существующая `bounds(concrete)`, если такая перегрузка определена;
- для Line2/3, Ray2/3 и Plane3 возвращается `UnsupportedOperation`;
- для Circle2 runtime-тесселяция вызывает `sampleCircle`;
- для Disk2, Rectangle2, Sphere3 и Box3 вызывается существующая `tessellate(concrete, options)`;
- остальные альтернативы тесселяции возвращают `UnsupportedOperation`.

Выбор веток выполняется через `if constexpr` по конкретному типу либо небольшие внутренние перегрузки. Успешное значение перемещается в соответствующую альтернативу variant; ошибка возвращается без изменения кода. Вызов конкретной перегрузки не должен рекурсивно выбирать runtime-перегрузку.

Альтернатива с ручным `switch` по `geometry.index()` отвергается: она дублирует порядок альтернатив и легче расходится с `Geometry` при расширении.

### 3. Point считается проверяемым при операции, а не неизменяемым объектом

Math Point не оборачивается и не делается закрытым: это сохранило бы видимость простоты Math, но потребовало бы ломающей замены публичных алиасов и отдельной модели преобразований. Вместо этого контракт явно различает проверку входа фабрики и проверку фактического значения операцией.

Runtime bounds для Point использует существующий `bounds(const Point<N>&)`, который уже возвращает `InvalidGeometry` для нечестных координат. Дополнительный общий валидатор Geometry не вводится: остальные типы закрыты и сохраняют инварианты, а неподдерживаемая тесселяция Point не должна имитировать вычисление над ним.

### 4. Результат владеет данными

Преобразование в variant использует `std::in_place_type<T>` и перемещение успешного typed-результата. Aabb копирует свои две точки; Polyline и TriangleMesh перемещают собственные контейнеры. Runtime-обёртки не возвращают span или ссылки на входной Geometry.

Состояние `valueless_by_exception` не передаётся в `std::visit`, поэтому `std::bad_variant_access` не становится частью нормального API. `std::bad_alloc` и текущая политика исключений остаются без изменений.

### 5. Координаты и роль типов фиксируются документацией

`docs/objectlib_usage.md` дополняется сигнатурами, таблицей поддерживаемых альтернатив и ошибками. В нём явно указывается:

- `Geometry` — закрытый каталог значений, а не обещание отображаемости или поддержки каждой операции;
- Aabb и TriangleMesh могут быть как самостоятельными входными значениями, так и результатами операций;
- фигуры с радиусом/размерами вычисляются в локальных координатах с центром в начале;
- явные точки сохраняют свои координаты;
- мировые преобразования и идентичность экземпляров относятся к будущему Core;
- изменяемый Point требует проверки в каждой операции, которая его использует.

Отдельные capability-варианты не добавляются до появления реальных потребителей в Core: текущие `UnsupportedOperation` и конкретные variant-результаты закрывают задачу без преждевременной классификации каталога.

## Risks / Trade-offs

- Новая альтернатива Geometry требует пересмотра обоих runtime-visitors → исчерпывающий `std::visit` и `if constexpr` сохраняют компиляцию контролируемой; тесты каталога дополняются новым типом при его появлении.
- Два результата-variant увеличивают публичную поверхность API → использовать их только там, где тип действительно выбран во время выполнения; typed API остаётся основным для известных типов.
- Делегирование сохраняет текущие ошибки, но не добавляет контекст поля или индекса → улучшение диагностики остаётся отдельным изменением.
- Runtime-обёртки не ограничивают время вычислений → существующие бюджеты тесселяции передаются без изменений, а сложность Polygon2 и отмена не входят в этот этап.
- Наличие общего `tessellate(Geometry)` может быть ошибочно понято как поддержка Polygon2 через `triangulate` → документация и тест UnsupportedOperation для Polygon2 явно различают эти операции.

## Migration Plan

Ломающей миграции нет. Существующий код продолжает использовать typed-перегрузки; новые перегрузки выбираются только при аргументе Geometry. Откат состоит в удалении добавленных declarations, runtime-реализации, тестов и документации без изменения форматов данных или состояния.
