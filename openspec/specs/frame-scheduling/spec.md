# frame-scheduling Specification

## Purpose
Определяет ограниченный асинхронный конвейер между Runtime и Renderer, который перекрывает подготовку и растеризацию без неограниченных очередей, потери ответов или преждевременного освобождения данных.

## Requirements

### Requirement: Неблокирующее принятие задания
Граница Renderer SHALL предоставлять неблокирующую отправку задания с явными результатами Accepted и Rejected и атомарной передачей владения снимком только при принятии.

#### Scenario: Задание принято
- **WHEN** транспорт принимает RenderFrame
- **THEN** возвращается Accepted, Runtime отмечает соответствующий frameId активным, а владение снимком переходит транспорту

#### Scenario: Задание отклонено
- **WHEN** транспорт не может принять RenderFrame
- **THEN** возвращается Rejected, владение снимком остаётся у Runtime, активное задание не создаётся и состояние занятости не устанавливается

### Requirement: Ограниченный конвейер кадров
Runtime SHALL допускать не более одного исполняемого Renderer-ом кадра и не более одного дополнительного подготовленного снимка; изменения Core SHALL не накапливаться в виде неограниченной очереди кадров.

#### Scenario: Подготовка во время рендеринга
- **WHEN** Renderer исполняет кадр и нет другого подготовленного снимка
- **THEN** главный поток может продолжать команды, update и подготовить не более одного следующего снимка без ожидания растеризации

#### Scenario: Подготовленный слот занят
- **WHEN** один следующий снимок уже подготовлен, а Renderer всё ещё занят
- **THEN** Runtime не создаёт дополнительную очередь снимков; последующие изменения накапливаются в Core до доступности подготовки

#### Scenario: Renderer освободился
- **WHEN** завершение активного кадра обработано и существует подготовленный снимок актуального поколения поверхности
- **THEN** Runtime может отправить его без ожидания новой подготовки

### Requirement: Однозначное завершение принятого кадра
Для каждого принятого задания при работающем исполнителе SHALL быть зарезервирована возможность доставить ровно одно FrameReady или FrameFailed без молчаливой потери результата.

#### Scenario: Успешная растеризация
- **WHEN** принятый кадр успешно обработан
- **THEN** Runtime получает FrameReady с frameId и владением framebuffer

#### Scenario: Ошибка растеризации
- **WHEN** принятый кадр завершается ошибкой
- **THEN** Runtime получает FrameFailed с frameId, освобождает активный слот и может продолжить следующие задания

#### Scenario: Канал результата занят
- **WHEN** обработчик завершает принятый кадр
- **THEN** место результата уже зарезервировано либо транспорт гарантирует эквивалентную надёжную доставку без блокировки исполнителя и потери владения

### Requirement: Корреляция завершений
Runtime SHALL изменять состояние активного задания только при совпадении frameId завершения с ожидаемым frameId.

#### Scenario: Позднее или чужое завершение
- **WHEN** полученное завершение не соответствует текущему активному frameId
- **THEN** Runtime диагностирует его и не освобождает слот текущего задания

#### Scenario: Повторное завершение
- **WHEN** после обработки завершения получено сообщение с тем же frameId
- **THEN** повтор не изменяет состояние нового задания и не передаёт повторно владение тем же framebuffer

### Requirement: Отдельный сигнал сбоя исполнителя
Адаптер SHALL доставлять RendererDown независимо от результата кадра; Runtime SHALL прекращать ожидание обычного завершения после подтверждённой смерти исполнителя.

#### Scenario: Исполнитель завершился без FrameFailed
- **WHEN** активный Renderer прекращает работу без штатного результата
- **THEN** Runtime получает отдельный сигнал сбоя, запрещает новые кадры и переходит к подтверждению окончания исполнения вместо бесконечного ожидания

#### Scenario: Таймаут без подтверждения смерти
- **WHEN** задание превышает ожидаемое время, но исполнитель продолжает работать
- **THEN** Runtime не освобождает используемые заданием ресурсы только по истечении таймаута

### Requirement: Поколение поверхности и resize
Runtime SHALL связывать кадр с поколением поверхности и отбрасывать завершённые кадры неактуального поколения без показа.

#### Scenario: Resize во время рендеринга
- **WHEN** размер поверхности изменился до обработки FrameReady
- **THEN** Runtime увеличивает поколение поверхности и освобождает кадр прежнего поколения без показа

#### Scenario: Нулевая площадь поверхности
- **WHEN** поверхность имеет нулевую площадь
- **THEN** Runtime не отправляет новые задания до появления ненулевого размера

### Requirement: Владение и переиспользование framebuffer
Владение framebuffer SHALL быть уникальным и явно передаваться между Renderer, Runtime и Presentation; буфер SHALL возвращаться в пул только после окончания использования.

#### Scenario: Синхронный показ
- **WHEN** Presentation полностью потребляет или копирует framebuffer до возврата из present
- **THEN** после возврата Runtime может безопасно передать буфер в пул переиспользования

#### Scenario: Асинхронный показ
- **WHEN** Presentation сохраняет использование framebuffer после возврата из вызова показа
- **THEN** возврат буфера в пул откладывается до отдельного подтверждения окончания использования

#### Scenario: Кадр устарел или отменён
- **WHEN** готовый framebuffer не показывается из-за resize или остановки
- **THEN** он освобождается или возвращается в пул без обращения к уже недействительной поверхности

### Requirement: Упорядоченная обработка главного цикла
Runtime SHALL обрабатывать события поверхности и resize до завершений Renderer, а команды и update SHALL завершаться до подготовки соответствующего снимка.

#### Scenario: Resize и FrameReady доступны вместе
- **WHEN** в одном проходе доступны resize и завершение прежнего поколения
- **THEN** сначала применяется resize, после чего прежний кадр отбрасывается без показа

#### Scenario: Команды доступны перед подготовкой
- **WHEN** в одном проходе есть принятые команды, игровые шаги и возможность подготовки
- **THEN** снимок строится после применения команд и ограниченного числа игровых шагов

### Requirement: Кооперативная остановка
При закрытии Runtime SHALL прекратить приём новых кадров и команд, явно отменить ожидающие команды и не уничтожать ресурсы до подтверждённого прекращения использования активного задания.

#### Scenario: Закрытие во время активного кадра
- **WHEN** запрошено закрытие при исполняемом кадре
- **THEN** новые кадры и команды отклоняются, ожидающие команды получают отмену, а готовый кадр не показывается

#### Scenario: Штатная остановка живого Renderer
- **WHEN** активное задание завершено и Renderer может принять Stop
- **THEN** Runtime отправляет Stop, получает Stopped и дожидается подтверждения прекращения исполнения до уничтожения каналов и ресурсов

#### Scenario: Остановка после RendererDown
- **WHEN** исполнитель уже завершился аварийно
- **THEN** Runtime не ожидает Stopped от умершего Renderer и использует подтверждение прекращения исполнения через адаптер
