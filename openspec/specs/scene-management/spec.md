# scene-management Specification

## Purpose
Определяет Core как владельца изменяемой игровой сцены и задаёт наблюдаемые правила создания, идентификации, размещения и обновления статических и динамических объектов простой игры.

## Requirements

### Requirement: Единый владелец сцены
Система SHALL хранить изменяемые экземпляры сцены только в Core. Object Library SHALL возвращать геометрические значения без назначения Scene ObjectId, регистрации экземпляра или запуска фоновой работы.

#### Scenario: Успешное создание экземпляра
- **WHEN** игровой код или редактор запрашивает создание объекта с допустимым геометрическим описанием
- **THEN** Core получает геометрическое значение, регистрирует экземпляр и возвращает его ObjectId

#### Scenario: Ошибка геометрического создания
- **WHEN** Object Library отклоняет геометрическое описание
- **THEN** Core не регистрирует экземпляр и оставляет сцену без частичных изменений

### Requirement: Обнаружение устаревших идентификаторов
Система SHALL назначать ObjectId, который однозначно обнаруживает обращение к уже удалённому или заменённому экземпляру слота.

#### Scenario: Обращение к удалённому объекту
- **WHEN** команда использует ObjectId ранее удалённого объекта
- **THEN** команда возвращает ошибку недействительного идентификатора и не изменяет другой объект

#### Scenario: Повторное использование слота
- **WHEN** после удаления объекта его внутренний слот используется для нового экземпляра
- **THEN** прежний ObjectId остаётся недействительным, а новый экземпляр получает отличимый ObjectId

### Requirement: Локальная геометрия и мировое размещение
Core SHALL отделять локальную геометрию от преобразования экземпляра и применять преобразование без неявного переноса явных координат в начало системы координат.

#### Scenario: Центрированная параметрическая фигура
- **WHEN** экземпляр центрированной фигуры размещается в игровом мире
- **THEN** её локальная геометрия остаётся центрированной, а мировое положение определяется преобразованием Core

#### Scenario: Геометрия с явными координатами
- **WHEN** экземпляр содержит mesh или polyline с явными локальными координатами
- **THEN** Core применяет к этим координатам преобразование экземпляра без дополнительного неявного смещения

### Requirement: Согласованная иерархия
Core SHALL поддерживать родительско-дочерние преобразования, отклонять циклы и применять определённое правило удаления поддерева.

#### Scenario: Перемещение родителя
- **WHEN** изменяется мировое преобразование родителя
- **THEN** мировые преобразования всех потомков обновляются с сохранением их локальных преобразований

#### Scenario: Создание цикла
- **WHEN** команда пытается назначить родителя, образующего цикл
- **THEN** Core отклоняет команду и сохраняет прежнюю иерархию

#### Scenario: Удаление поддерева
- **WHEN** удаляется объект, имеющий потомков
- **THEN** всё поддерево удаляется атомарно, а обращения к любым удалённым ObjectId после завершения команды отклоняются

### Requirement: Разделяемая геометрия экземпляров
Система SHALL позволять нескольким экземплярам использовать одну неизменяемую геометрию с независимыми преобразованиями и визуальными параметрами.

#### Scenario: Два экземпляра одной геометрии
- **WHEN** два объекта ссылаются на одну геометрию и имеют разные мировые преобразования
- **THEN** изменение или удаление одного экземпляра не изменяет геометрию и состояние другого экземпляра

#### Scenario: Замена геометрии ресурса
- **WHEN** Core заменяет геометрию в разделяемом ресурсе
- **THEN** уже выданные неизменяемые представления прежней версии остаются действительными до окончания их использования

### Requirement: Статические и динамические объекты
Core SHALL поддерживать статическую и динамическую mobility-разметку как подсказку для оптимизации, не запрещая последующее изменение статического объекта.

#### Scenario: Движение динамического объекта
- **WHEN** игровая система изменяет локальное преобразование динамического объекта
- **THEN** Core обновляет связанное мировое состояние без замены его локальной геометрии

#### Scenario: Изменение статического объекта
- **WHEN** явная команда изменяет преобразование или геометрию статического объекта
- **THEN** Core применяет изменение и инвалидирует только зависимые от него производные данные

### Requirement: Атомарное упорядоченное применение команд
Система SHALL применять принятые команды сцены последовательно в порядке приёма на выделенном потоке Core и возвращать результат каждой принятой команды.

#### Scenario: Несколько изменений в одном проходе
- **WHEN** Runtime применяет пакет принятых команд перед обновлением мира
- **THEN** последующее обновление и подготовка кадра наблюдают результат всех успешно применённых команд в порядке приёма

#### Scenario: Невалидная команда в пакете
- **WHEN** одна из команд пакета невалидна
- **THEN** эта команда не производит частичных изменений, а результаты остальных команд сохраняют собственный порядок и статус

### Requirement: Ограниченное догоняющее обновление
Core SHALL выполнять игровое обновление с фиксированным настраиваемым шагом, а Runtime SHALL ограничивать число догоняющих шагов за проход главного цикла.

#### Scenario: Обычный игровой тик
- **WHEN** накоплено достаточно времени для одного фиксированного шага
- **THEN** игровые системы получают один update с этим шагом до подготовки следующего кадра

#### Scenario: Длительная пауза главного цикла
- **WHEN** накопленное время требует больше обновлений, чем разрешённый предел
- **THEN** выполняется не более разрешённого числа шагов, избыток целых шагов отбрасывается и учитывается в диагностике, а дробный остаток сохраняется

### Requirement: Чтение сцены без изменяемых ссылок
Потребители вне Core SHALL получать результаты запросов или отдельные представления сцены, а не изменяемые ссылки на внутренние элементы Core.

#### Scenario: Чтение состояния редактором
- **WHEN** редактор запрашивает представление сцены после применения команд
- **THEN** представление отражает завершённые изменения и не позволяет изменить Core в обход команд или игровых систем
