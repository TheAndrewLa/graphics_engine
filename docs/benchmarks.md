# Нагрузочные сценарии, телеметрия и baseline производительности

В документе зафиксированы архитектура телеметрии кадра, методика профилирования конвейера движка Huynity и baseline-показатели для шести ключевых игровых сценариев. Реализация сценариев и автоматические проверки инвариантов размещены в `tests/integration/benchmark_tests.cpp` (таргет `huynity_benchmark_tests`, CTest `integration.benchmarks`).

---

## 1. Архитектура телеметрии кадра (`FrameTelemetry` / `BenchmarkMetrics`)

Сбор метрик организован по фазам кадра и структурным подсистемам:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                             FrameTelemetry                                  │
├──────────────────┬─────────────────┬───────────────────┬────────────────────┤
│   PhaseTimings   │  DirtyMetrics   │   CacheMetrics    │  GeometryMetrics   │
│ ──────────────── │ ─────────────── │ ───────────────── │ ────────────────── │
│  • updateUs      │ • dirtyTransforms│ • tessHits/Calcs │ • objectCount      │
│  • prepareUs     │ • dirtyBounds   │ • shadingHits/Miss│ • drawItemCount    │
│  • renderUs      │                 │ • hit rates       │ • triangleCount    │
│  • presentUs     │                 │                   │                    │
│  • totalUs       │                 │                   │                    │
├──────────────────┴─────────────────┴───────────────────┴────────────────────┤
│                BufferPoolMetrics                   PipelineMetrics          │
│                ─────────────────                   ───────────────          │
│                • allocations (created)             • ready                  │
│                • pooled                            • rejected               │
│                • maxPooled                         • dropped (stale)        │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Структуры данных

1. **`PhaseTimings`**:
   - `updateUs`: время применения команд и игрового обновления фиксированного шага (`FixedStepUpdate`);
   - `prepareUs`: время сбора пространственного состояния, отсечения (culling), тесселяции и формирования `RenderSnapshot`;
   - `renderUs`: время программной растеризации активных passes (World3D с depth test и flat shading, World2D, Hud2D с alpha blending);
   - `presentUs`: время синхронной или асинхронной передачи буфера в порт показа `PresentationPort`;
   - `totalUs`: суммарное время кадра по всем фазам.

2. **`DirtyMetrics`**:
   - `dirtyTransformUpdates`: число объектов сцены, для которых изменился `worldTransform` за текущую итерацию;
   - `dirtyBoundsUpdates`: число объектов сцены с взведённым флагом `dirty.bounds`, потребовавших пересчёта мирового AABB в `refreshSpatialState()`.

3. **`CacheMetrics`**:
   - `tessellationHits` / `tessellationCalculations`: число повторных использований готовой тесселяции и новых вычислений в `TessellationCache`;
   - `shadingHits` / `shadingMisses`: число обращений к кешу нормалей граней `ShadingDataCache` и вычислений новых нормалей для mesh-ресурсов;
   - `hitRate`: отношение `hits / (hits + misses)`.

4. **`GeometryMetrics`**:
   - `objectCount`: общее число зарегистрированных в сцене объектов;
   - `drawItemCount`: суммарное количество элементов отрисовки по всем проходам снимка;
   - `triangleCount`: общее число треугольников, поданных на растеризацию.

5. **`BufferPoolMetrics`**:
   - `allocations`: общее количество созданных `ImageBuffer` за время жизни пула (`FramebufferPool::createdCount()`);
   - `pooled`: количество готовых свободных буферов в пуле (`FramebufferPool::pooledCount()`);
   - `maxPooled`: максимальная ёмкость пула (`FramebufferPool::maxPooled()`).

6. **`PipelineMetrics`**:
   - `ready`: количество успешно завершённых и переданных на показ кадров (`FrameOutcome::Ready`);
   - `rejected`: количество отклонённых транспортом попыток отправки кадра при занятом исполнителе (`SubmitResult::Rejected` / `DispatchResult::Rejected`);
   - `dropped`: количество отброшенных устаревших кадров или подготовленных снимков при смене поколения поверхности (`FrameOutcome::Stale` / `DispatchResult::DroppedStale`).

## 2. Методика замеров

1. **Изоляция прогрева и устойчивого режима (steady state):**
   - **Кадр 0 (init / warmup):** первичное наполнение кешей тесселяции, расчёт нормалей геометрии, первая аллокация кадрового буфера в `FramebufferPool`.
   - **Кадры 1..N (steady state):** контрольные замеры времени и попаданий в кеши в стабильном режиме работы.
2. **Точный подсчёт dirty-состояний:**
   - Перед вызовом `prepareSnapshot` инспектируются флаги `dirty.bounds` и ревизии `revisions.worldTransform` каждого экземпляра.
   - Метод `refreshSpatialState()` снимает флаги `dirty.bounds`, поэтому на последующих статических кадрах число обновлений равно нулю.
3. **Контроль аллокаций памяти:**
   - Отслеживается счётчик `FramebufferPool::createdCount()`. В устойчивом режиме после кадра 0 новые аллокации буферов отсутствуют (100% reuse).
   - Для ресурсов геометрии проверяется `snapshot.resources3.size() == 1`, подтверждающий отсутствие дублирования массивов вершин при множественных экземплярах.
4. **Симуляция обратного давления конвейера (backpressure 1+1):**
   - Используется `FakeRendererAdapter`, имитирующий асинхронную задержку рендерера.
   - Проверяется запрет подготовки снимков (`canPrepare() == false`), когда prepared-слот уже занят, исключающий бесполезную трату ресурсов CPU.

## 3. Baseline-показатели 6 нагрузочных сценариев

Все замеры приведены для разрешения 64×64 (эталонный headless-размер интеграционных тестов) в сборке Debug (GCC 14, -O0, Linux x86_64).

### Сценарий 1: `static` (128 статических 3D-объектов)
- **Конфигурация:** 128 кубов (`Box3`), расположенных в сетке 16×8, `Mobility::Static`, ортографическая камера 3D, направленный и рассеянный свет.
- **Поведение:**
  - В кадре 0 происходит первичная тесселяция 128 кубов (128 вычислений) и расчёт нормалей (128 промахов кеша шейдинга).
  - В последующих кадрах сцена не мутирует.
- **Baseline-метрики steady state (за 10 кадров):**
  - Dirty updates: `transforms = 0`, `bounds = 0` (0% накладных расходов на пространственное дерево).
  - Кеш тесселяции: **100.0% hits** (1280 hits, 0 calculations).
  - Кеш shading-данных: **100.0% hits** (1280 hits, 0 misses).
  - Пул буферов: 1 аллокация на старте, **100% повторное использование** (0 новых аллокаций).
  - Средние фазовые тайминги:
    - Update: ~1-2 мкс;
    - Prepare: ~370-450 мкс;
    - Render: ~1000-1150 мкс;
    - Present: <1 мкс;
    - Total: ~1.4-1.6 мс.

### Сценарий 2: `moving instances` (128 динамических экземпляров общей геометрии)
- **Конфигурация:** 1 исходный `Box3`, 128 динамических экземпляров (`Mobility::Dynamic`), разделяющих единый `shared_ptr<const Geometry>`, смещаемых каждый кадр.
- **Поведение:**
  - В кадре 0 геометрия куба тесселируется **ровно 1 раз**; 127 экземпляров сразу получают результат из кеша.
  - При движении каждый кадр меняются только локальные матрицы 128 экземпляров.
- **Baseline-метрики (за 5 кадров движения):**
  - Dirty updates: строго 128 dirty transforms и 128 dirty bounds на кадр.
  - Кеш тесселяции: **100.0% hits** (0 пересчётов тесселяции при движении, 640 hits).
  - Идентичность геометрии: `snapshot.resources3.size() == 1` — **0 копий геометрии**, все 128 draw items ссылаются на mesh 0.
  - Кеш shading-данных: **100.0% hits** (640 hits, 0 misses, так как нормали в локальном пространстве сетки неизменны).
  - Пул буферов: 1 аллокация, 100% reuse.
  - Средние фазовые тайминги:
    - Update: ~17-19 мкс;
    - Prepare: ~490-510 мкс;
    - Render: ~980-1010 мкс;
    - Total: ~1.5 мс.

### Сценарий 3: `geometry edits` (изменение геометрии 1 объекта из 100)
- **Конфигурация:** 100 объектов с индивидуальной геометрией. В контрольном кадре вызывается `scene.setGeometry(targetId, newBox)` ровно для одного объекта (индекс 42).
- **Поведение:**
  - Изменение геометрии увеличивает `geometryVersion` целевого объекта и выставляет `dirty.tessellation = true`.
  - Все остальные 99 объектов сохраняют свои кеши.
- **Baseline-метрики кадра редактирования:**
  - Dirty updates: 0 dirty transforms, 1 dirty bounds.
  - Кеш тесселяции: **ровно 1 пересчёт** (для изменённого объекта) и **ровно 99 попаданий** в кеш (для неизменных).
  - Кеш shading-данных: **ровно 1 промах** (пересчёт нормалей для обновлённой сетки) и **ровно 99 попаданий** в кеш.
  - В следующем кадре без изменений: 100% попаданий (100 hits, 0 calculations).
  - Средние фазовые тайминги: Prepare ~290 мкс, Render ~1000 мкс.

### Сценарий 4: `2D-only` (100 World2D-объектов + 10 элементов HUD)
- **Конфигурация:** 100 прямоугольников в `World2D` (слои 0..2) и 10 элементов интерфейса в `Hud2D`. 3D-камера отключена (`camera3 = nullopt`).
- **Поведение:**
  - Полное отсутствие 3D-освещения и depth buffer: снимок содержит только `World2DPass` и `Hud2DPass`, `resources3.empty() == true`.
  - Растеризация алгоритмом художника с alpha blending.
  - Проверка инварианта стабильной сортировки: элементы отрисовки в проходах строго упорядочены по кортежу `(layer, order)`.
- **Baseline-метрики:**
  - Треугольники: 100 × 2 (World2D) + 10 × 2 (HUD) = 220 треугольников.
  - Кеш шейдинга: 0 обращений (3D normal calculations не требуются).
  - Средние фазовые тайминги:
    - Prepare: ~250 мкс (быстрее 3D на 30-40%);
    - Render: ~540-560 мкс (быстрее 3D в ~2 раза за счёт отсутствия z-buffer и освещения);
    - Total: ~0.8 мс.

### Сценарий 5: `3D+HUD` (100 World3D-объектов + 10 элементов HUD)
- **Конфигурация:** 100 3D-кубов в `World3D` с освещением (ambient + directional light) + 10 полупрозрачных HUD-прямоугольников в экранном пространстве.
- **Поведение:**
  - Снимок содержит `World3DPass` (100 draw items) и `Hud2DPass` (10 draw items).
  - Flat shading и depth testing разрешают перекрытия 3D-сцены, поверх которой с alpha blending накладывается HUD.
- **Baseline-метрики (steady state):**
  - Треугольники: 100 × 12 (кубы) + 10 × 2 (HUD) = **1220 треугольников**.
  - Кеш тесселяции: **100.0% hits** (550 hits за 5 кадров, 0 calculations).
  - Кеш shading-данных: **100.0% hits** (500 hits за 5 кадров, 0 misses).
  - Пул буферов: 1 аллокация, 100% reuse.
  - Средние фазовые тайминги:
    - Prepare: ~300-320 мкс;
    - Render: ~900-950 мкс;
    - Total: ~1.2-1.3 мс.

### Сценарий 6: `slow Renderer` (симуляция медленного рендерера и обратного давления)
- **Конфигурация:** `FramePipeline` + `FakeRendererAdapter` + `CompletionChannel` + `SimpleSyncPresentationPort`.
- **Поведение и инварианты конвейера 1+1:**
  1. **Приём кадра 1:** отправка успешна (`Accepted`), адаптер переходит в состояние `isBusy() == true`.
  2. **Подготовка кадра 2 во время рендера кадра 1:** `canPrepare() == true`, кадр 2 помещается в единственный prepared-слот (`storePrepared == true`).
  3. **Обратное давление (backpressure):**
     - Пока кадр 1 исполняется, а кадр 2 ожидает в слоте, **`canPrepare() == false`**.
     - В главном цикле `runIteration` лямбда подготовки снимка **даже не вызывается**, исключая лишнюю нагрузку на процессор.
     - Прямая попытка отправки в занятый порт возвращает `SubmitResult::Rejected` (счётчик `rejected` увеличивается на 1).
     - Попытка `dispatchPrepared` при занятом адаптере возвращает `DispatchResult::Empty`.
  4. **Освобождение исполнителя:** завершение кадра 1 через `completeReady()` возвращает `FrameOutcome::Ready`, буфер кадра 1 отдаётся в презентацию и возвращается в пул.
  5. **Диспетчеризация отложенного кадра:** освободившийся адаптер немедленно принимает кадр 2 (`DispatchResult::Submitted`).
  6. **Отсечка при смене поколения поверхности (resize):**
     - Подготовленный снимок прежнего размера при `resize()` автоматически уничтожается (`dropped` + 1).
     - Завершившийся на адаптере кадр прежнего размера помечается как `FrameOutcome::Stale`, отбрасывается без показа (`dropped` + 1), а его буфер уничтожается пулом.
  7. **Пул кадровых буферов:** число одновременно живых буферов строго ограничено (не более `maxPooled + 1` при активном рендере), утечки памяти отсутствуют.

## 5. Запуск и воспроизведение

Для прогона тестов производительности и проверки baseline:

```sh
HUYNITY_BUILD_DIR="$PWD/build"
cmake --build "$HUYNITY_BUILD_DIR" --target huynity_benchmark_tests
ctest --test-dir "$HUYNITY_BUILD_DIR" -R '^integration.benchmarks$' --output-on-failure --verbose
```
